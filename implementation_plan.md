
`env.ps1` affects only that PowerShell window; nothing changes system-wide. It:

### Funding stages

The client (the student's side) funds the Anthropic API usage, up to about $150. That is a lot of money for them, so **we never ask for money ahead of evidence**. Funding is released in stages, each only after the previous stage shows working output. **The money buys test runs, not outcomes.** We promise a fair, reproducible comparison, not that the enhancement beats the baseline or the index.

| Stage | When | Key and budget | What it buys | Gate to move on |
|---|---|---|---|---|
| 0 | Now (Phases 1–5) | Personal key, ₹300 (use $3.00; auto-stop at $2.40) | Build and prove the pipeline on small slices (5–20 stocks, 3–12 months), Haiku only; measure real token counts | Pipeline runs end to end on small slices; leak tests and red-flag checks pass; cost forecast v1 |
| 1 | ~Week 3 (start of Phase 6) | Student key, ~$20 | Sonnet pilot; thinking on/off decision; a first baseline slice on the `paper` tier | Measured cost per rebalance for each variant; thinking decision recorded; cost forecast v2 |
| 2 | After the forecast is shared and approved | Student key, ~$80–90 | Full 2015–2023 runs: baseline (Phase 6), enhanced and names-hidden (Phase 7) | Forecast (±20%) approved by you |
| Contingency | Only if the forecast shows a need | Up to the $150 total | Reruns, or thinking turned on | Your explicit approval |

**How it is enforced (built in Phase 3, used from then on):**
1. **Per-stage budgets in config** (`configs/stages.yaml`; the active stage is `budget.stage`). The cost ledger tracks spend per key label **and per stage**. It stops automatically at **80% of the stage budget** and tells you. It never crosses into the next stage's budget without your explicit approval (changing `budget.stage` is that approval, and only you ask for it).
2. **Cost forecast report** `docs/cost_forecast.md`, generated by `scripts/cost_forecast.py` from measured ledger data at the end of Stage 0 and again at the end of Stage 1. It shows:
   - measured tokens and cost per rebalance, for each variant (baseline, enhanced, names-hidden) and each model setting;
   - projected cost of each full run, the total, and a ±20% range;
   - the cache hit rate and its effect on cost;
   - costs in USD and INR (configurable rate);
   - a one-paragraph plain-language summary you can forward to the client.

   Variants not yet built when a forecast is made (enhanced and names-hidden are built in Phase 7) are shown as *estimated from baseline measurements*, clearly labelled. The forecast is re-issued with measured numbers before their full runs.
3. **Stage gate checklist.** At each gate I stop and give you:
   - what was built and run in this stage;
   - the evidence that it works: tests passed, sample outputs, checks;
   - actual spend vs. budget for the stage;
   - the forecast for the next stage;
   - the exact amount to request next.

   I don't start the next stage until you confirm the funds are approved and the key is in place.
4. **No wasted spend:**
   - the response cache does not depend on the API key, so cached responses survive key swaps;
   - crashed runs resume from checkpoints without paying again;
   - never a full backtest to debug; debugging happens on small slices.
5. **Deliverables don't depend on a win.** Whatever the result, the project delivers the working system, baseline vs. NASDAQ-100 results, the decision transcripts, the poster materials and the handoff docs. If the enhancement doesn't outperform, it's reported honestly, with analysis of why.

## Recommendations adopted

| # | Question | Decision |
|---|---|---|
| R1 | Membership source | **Free reconstruction.** Start from the current NASDAQ-100 list and replay Wikipedia's yearly change tables backwards, cross-checked against Nasdaq's annual reconstitution announcements. The result is a versioned file, `reference/ndx_membership.csv`, with one row per membership spell: ticker, start, end, source. The source sits behind an interface, so a paid dataset (Norgate, or CRSP via WRDS) can replace it later without code changes elsewhere. |
| R2 | Delisted prices | yfinance first. Any gaps can be filled from your own CSV files in `D:\CreatED-Quant\qa_store\manual_prices\` (same adapter interface). A member that still has no price data on a date is left out of that date's universe, and its index weight is redistributed. Every such case is logged, and a coverage report shows the % of index weight missing per date. A red flag is raised if more than 2% is missing. |
| R3 | Success criterion | Information ratio vs. the NASDAQ-100 and Carhart 4-factor alpha, alongside Sharpe, Sortino and max drawdown. **To be confirmed with the professor before any full-run result is shown.** All metrics are computed regardless. |
| R4 | Sector band | ±2 percentage points (`sector_band_pp: 2.0`). |
| R5 | Rating → return table | The brief's defaults (−6 / −3 / 0 / +3 / +6 %). Converted to a monthly figure by dividing by 3 (simple compounding); documented in `design.md`. |
| R6 | Index weights | Plain derived cap weights: shares outstanding from EDGAR (by filing date) × price, normalized across members. Nasdaq's capping rules are **not** copied. We validate by comparing our derived index with QQQ and report the tracking error. ~~GOOG and GOOGL stay as two members~~ → **company level (D27, 6 Nov)**: share classes are one company whose weight is the sum of its classes. |
| R7 | Sector and country | Sector comes from the SEC industry code (SIC), mapped to 11 GICS-like sectors in `reference/sic_to_sector.csv`. HQ country comes from the EDGAR business address. Neither is a GICS licence. Both are static per company. |
| R8 | Geography | Reported and checked (weights by country vs. the index), **not** enforced as a band. |
| R9 | Decision timing | `as_of` is the **close (4 pm ET) of the first trading day of the month**. News published before 4 pm that day counts. Trades happen at the next trading day's open. |
| R10 | Package layout | The brief's layout, placed inside one Python package `quantagents/` (e.g., `quantagents/data/gateway.py`). This avoids clashes with other libraries named `data` or `eval`. `configs/`, `tests/`, `scripts/`, `reference/` and `docs/` sit at the repo root. |
